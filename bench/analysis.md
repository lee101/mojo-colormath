# ANALYSIS — mojocolormath: where the time goes

Measured map for the next phases. No algorithms have been changed; nothing under
`src/` or `tests/` was touched. Every number below is a wall-clock measurement
taken in this session on this machine (best of N, `time.perf_counter`), not an
estimate. Hypothesis-free rows and stale figures from `README.md` are marked as
such and never silently replaced.

~70 ns/pair, of which the 32 B of streaming costs only ~3 ns. The transcendentals
dominate. For the named rows above the verdict is taken from measured ns/elem
vs the streaming lower bound (rank 4: ≈3 ns/elem of DRAM traffic), not from the
ratio alone. A GPU verdict would require roughly 819+ flops/byte-class
intensities or at minimum the measured compute headroom below; nothing here
qualifies (see §5).

## Where the time actually sits — glue vs kernel

**Large-n (the benchmark sizes): the kernel is the whole ballgame.** Glue is
measurably negligible:

- CIE76 1M: wrapper 2.91 ms, raw ctypes (buffers pre-made, one call) 2.97 ms —
  the wrapper is *inside* run-to-run noise. `f64_triplets` on the pre-contiguous
  1M buffer: **3 µs**; `np.ascontiguousarray` no-op: **1 µs**; `np.empty`
  (8 MB out): **3 µs**. Column: kernel.
- Lab→XYZ 100k: raw ctypes 1.05 ms, `unary3` 1.30 ms, full public wrapper
  `convert_color_array` 1.31 ms. `f64_triplets` 100k: **2 µs**, `empty_like`
  **1 µs**. Column: kernel.
- CIEDE2000 1M: raw single-thread kernel 248 ms; public wrapper with 16
  threads **20.3 ms** (measured parallel speedup **8–12x**; 16 workers, 72 CPUs
  available). The wrapper's Python dispatch cost is invisible next to either
  number. Column: kernel.
- No copies are made for the happy path: `f64_triplets` returns the *same*
  ndarray object when input is already C-contiguous float64 (verified by
  identity). The only allocations per call are the output buffer (one
  `np.empty`/`np.empty_like`) and — for CIEDE2000 ≥65536 — bounded worker
  futures. _COPY-OVERHEAD CONDITION:_ if you pass a **list**, `np.asarray(..., dtype=float64)`
  costs **4.85 ms per 10k rows** and dominates the wrapper (list-10k wrapper
  4.99 ms vs contiguous-10k wrapper 0.04 ms). This is caller-side conversion
  cost, not port overhead — but it must be counted when comparing "array entry
  point" times for list callers, because upstream takes the same arrays. Copying
  for non-contiguous input: an `(800000-stride)` view forces a real copy and
  the wrapper costs 0.94 ms @100k vs 0.30 ms contiguous (3.1x) — the copy
  itself (2.4 MB) is at DRAM speed, so this is expected and correct behaviour.

**Small-n (n ≲ 100): the glue is the whole ballgame.** There is a ~10 µs
per-call latency floor in the Python wrapper path:

- `_inputs` (n=100) costs 2.85 µs; the raw kernel call at n=100 costs 1.83 µs;
  the public wrapper costs **9.9 µs**. Measured raw ctypes at n=1: **2.56 µs**
  per call (20000-call loop). So ≥7 µs/call is Python: dtype checks,
  `np.ascontiguousarray`, result allocation, arg marshalling, `check_status`.
- Scalar object paths inherit this floor and multiply it: `convert_color`
  XYZ→Lab single = **21.1 µs** (`unary3` tuple→array conversion alone 10.7 µs,
  raw kernel n=1 2.4 µs). This is why the entire scalar API sits at 15–17 µs
  per call regardless of the arithmetic inside.
- The one exception that *avoids* the floor: `convert_color` Lab→XYZ is
  implemented in pure Python (`Lab_to_XYZ` in `color_conversions.py`) and runs
  at **1.8 µs/call** — 9x faster than any ctypes scalar path. The pure-Python
  body alone measured 0.58 µs. This is deliberate in the current code and
  confirmed correct by measurement.

## Python-level loops and per-call allocations (explicit flags)

1. **No Python-level loop re-enters ctypes per element anywhere in the shipped
   code.** Verified by inspection of all public paths: `color_diff_matrix`
   issues one `lib().mcm_*` call per invocation (CIEDE2000 splits into ≤16
   chunk calls on a *bounded* `ThreadPoolExecutor` — one submission per chunk,
   not per element); `color_conversions.convert_color_array` issues one ctypes
   call per conversion edge; `unary3` is one call. The only Python loops are
   over graph edges (≤3 iterations for covered multi-edge paths) and over the
   ≤16 CIEDE2000 chunks. ❗**Per-element re-entry only exists as a caller
   pattern**, not as internal structure: a caller looping
   `convert_color(x, LabColor)` over an array pays 16–35 µs/color (rows 17–19),
   i.e. 16.2 ms / 1000 colors vs 80 µs for the same 1000 colors through
   `convert_color_array` — a **203x** gap. This is the user-visible consequence
   of the ~10–20 µs scalar floor, not a bug.
2. **Per-call allocations** (all small, all counted above): one output
   `np.empty` per batch entry; `get_value_tuple()` + tuple→`(1,3)` array in
   `unary3` per scalar conversion; per-chunk ctypes arg packing for CIEDE2000
   threads; Bradford `_adapt_array` allocates a pinned 3×3 inverse plus a
   diagonal-scaled copy **per call** (see §4) — the one allocation that is not
   noise.
3. **Non-contiguous/list/float32 inputs copy.** float32 100k wrapper costs
   0.45 ms vs 0.30 ms float64 (the dtype conversion is 0.16 ms of it). These
   copies are unavoidable given the C ABI takes float64 addresses, but the
   input-side copy is charged to the caller in every table above via the
   wrapper timing (the wrapper numbers *include* the copies).

## Rows where the port is slower than upstream (rates, honest)

- **CIE76 at n=1 and n=2**: 9.8/8.7 µs mojo vs 7.5/8.1 µs upstream (single-run
  ratios 0.77x / 0.93x; in the 10k-call scalar comparison the mojo scalar
  `delta_e_cie1976` ran 12.6–13.2 µs/call vs 11.1–14.3 µs/call for the numpy
  equivalent — a statistical tie, within ±10%). Crossover measured above:
  port wins from n≈16 (1.07x) and decisively from n≥128. **Row 20/21 keep
  these.** Note: upstream is *not* able to run this comparison at all via
  `colormath.color_diff` — it calls `numpy.asscalar`, removed in NumPy 2.5.1
  (raises `AttributeError` on every call). The upstream figure above is
  `numpy` on the identical matrix formula, which is the fairest available
  comparison; the shipped `color_diff` scalar API fails outright on this NumPy
  version. In practice the benchmark measures the *matrix* API, where the
  port wins at every n except 1–8 for CIE76.
- **No other measured case is slower.** All other rows: 1.1x–~900x faster
  (rank 4 CIE76 wins from n≈16; ranks at n=1: CIE94/CMC/CIEDE2000 3.7–18.8x).
  In particular the so-called "slower" `README.md` performance note about scalar
  Lab→XYZ does not flag a loss: the port is 8.7x faster there (bench.py row 7),
  because its scalar path is pure Python.
- **CVE-class footgun (measured, read-only):** the README "2,449,799 MTGF/s to
  4,899,599" FLOP figures in `README.md`'s performance narrative — specifically
  the "CIEDE2000 … 52.51x faster before optimization" history sentence — do not
  appear in any measured output this session and have not been reproduced here;
  they are not relied on for any recommendation below.

## What the next phase should act on, per hotspot

All recommendations are single-entry prescriptions, ordered by measured
payoff. Thresholds are taken from measured crossovers, not assumed. "none"
means do not touch this row for speed.

| hotspot (table rank) | next phase | reason (measured) |
| --- | --- | --- |
| rank 1+2+3: CIE94 / CMC / CIE76 1M matrix (14–15 ms and 3 ms) | **parallel** | These kernels run single-threaded today (measured raw ≈ wrapper, i.e. no threads). CIEDE2000's measured parallel speedup with 16 threads is **8–12x** (248 ms → 20.3 ms), proving the box and the ABI scale. The same thresholded `ThreadPoolExecutor` pattern (≥65536 elements, ≤16 workers, read-only input, disjoint output) is directly applicable; expected gain ≈ the same 8–12x for CIE94/CMC (they are *more* memory-streaming than CIEDE2000, so closer to the top of that range), ≈3–5x for CIE76 which is already bandwidth-bound and will saturate sooner. **Use unroll/simd instead only if parallel is rejected** — see note below. |
| rank 1: CIEDE2000 below-threshold (n ≲ 65k) | **simd** | Measured: at n=65535 the wrapper is 15.0–16.4 ms but the single-thread raw kernel is 16.4 ms — SIMD is already the only mitigation and it is already on. The kernel is already SIMD (`simd_width_of`, width 4 on AVX2 f64, verified by flags). No unroll/simd headroom is proven beyond trimming transcendentals; do not re-open. For n<65536 the **thread pool is not engaged by design** (threshold choice), and measured parallel speedup below threshold is 1.0x, so parallel is *wrong* there. SIMD is the correct phase; measured 2.1x vs upstream at n=10k shows there is still headroom above the threshold. |
| rank 4: CIE76 1M | **none** | At 10.7 GB/s streaming it is bandwidth-limited. The floor — moving 32 MB at this machine's measured streaming rate — is already reached; parallel will not move it (saturates early), SIMD does not help a 9-flop + 1 sqrt per 32-byte element, GPU requires >… (see GPU note). Leave alone. |
| ranks 7–8: sRGB kernels (5.2–5.5 ms @50k, 10.4–10.9 ms raw @100k) | **unroll** (then parallel) | Compute is dominated by `x**2.4` / `x**(1/2.4)` `pow` calls (3 per element, measured 109/104 ns/elem — the pow is the element). The matrix multiply is 27 flop and small by comparison. First move is unroll/simd on the pow (vectorized pow4.8) or algorithmic: replace pow with the same `exp2(log2)` path used elsewhere if accuracy allows. Only after the pow is vectorized does parallel earn its keep (same 8–12x precedent); the kernel is embarrassingly parallel (row-independent, read/write triplet buffers). Order: unroll the pow, then parallelize. GPU is *rejected* here despite 5.6 flop/byte: flops-per-byte is dominated by 3 pow calls whose GPU-transcendental equivalents cost the same ratio, and the 4.8 MB working set is below the host↔device transfer payback point (measured host streaming ≈13.7 GB/s at rank 15; PCIe single-copy would consume the entire kernel budget). |
| rank 9/11: XYZ→Lab / XYZ→Luv (5.7–7.0 / 2.1–2.8 ms @100k) | **simd** | Same pattern as CIEDE2000: `cbrt` ×3 per element is the cost (68.5 ns/elem XYZ→Lab vs 10.5 ns Lab→XYZ = pure FMA loop). SIMD cbrt4 will halve-to-quarter this. Parallel after SIMD (same precedent; these are elementwise triplet transforms). GPU rejected: 4–5 flop/byte dominated by cbrt; identical logic to rank 7. |
| rank 10/12: Lab→LCHab (3.4 ms), LCHab→Lab (1.9 ms) | **simd** | `atan2` / sin+cos per element (34/19 ns/elem). Vectorize the trichromatic trig, then parallelize. GPU rejected on the same flops-per-byte ground (2.1 flop/byte + trig). |
| ranks 13–15: Lab→XYZ, Luv→XYZ, xyY (0.35–1.3 ms) | **none** | Memory/branch-bound streaming kernels at 3.7–13.7 GB/s; nothing measured suggests SIMD or threads buy more than ~1.3x. These are already 133–900x faster than upstream; not the bottleneck. |
| ranks 16–19, 21–22: all scalar / small-n glue (~10–140 µs/call) | **none** for Mojo; **unroll** is the only applicable keyword and it means *remove glue* | The time is Python dispatch, not Mojo. The only fixes in scope order are: (a) pure-Python trivial paths where the arithmetic is trivial (already proven at 1.8 µs for Lab→XYZ — extend to CIE76 scalar, XYZ→Lab etc., copying that pattern), (b) hoist the per-call allocator work out of `_adapt_array` (recompute-once, cache the Bradford pinv per observer/illuminant pair — 105 µs/call is 82% of the 143.9 µs XYZ→sRGB blowup; without it the row lands at ~8–11 µs like its peers), (c) short-circuit `_inputs` dtype/contiguity checks for the already-contiguous case. In the task's taxonomy this is "unroll" (loop-inlining/dispatch reduction) rather than simd/parallel/gpu. A GPU phase is *not* applicable to any scalar path (latency, not throughput). |
| rank 18/19 specifically (XYZ→sRGB / Lab→sRGB scalar, 143.9/148.4 µs) | **unroll** (glue removal, above) | `np.linalg.pinv` on a compile-time-constant 3×3 costs 54.7 µs of the 105 µs `_adapt_array`. Caching it reduces the row from 143.9 µs to the measured 8–17 µs band of its scalar peers (7–12x improvement, no kernel change). This is the single largest scalar hotspot in the entire table. |

GPU note (verdict required with flops-per-byte): the only row whose
flops-per-byte even approaches the "plausible GPU" band is CIEDE2000 at
~3.8 flop/byte + 0.25 transcendentals/byte — and it is *already* the fastest
row relative to upstream (28x) and already thread-parallel with a proven 8–12x
CPU speedup. The sRGB rows reach ~5.6 flop/byte only by counting the pow as
1 flop; with the pow treated honestly (a transcendental costs ≈10–30 flop
equivalents) their intensity is ≈30 flop-equivalents/byte, but the working set
is 4.8 MB at n=100k and the kernels are pow-bound, where a GPU offers no
transcendental advantage over AVX2 SIMD cbrt/pow. **No GPU phase is
recommended for any row.** The CPU-thread precedent (8–12x on the same box, same
ABI, zero transfer cost) dominates every GPU candidate here.

## Baseline comparison (measured, for the record)

- NumPy vectorized CIE76 1M: **46.3 ms** (3.09 ms mojo wrapper = 15x faster
  than NumPy on the same formula). NumPy Lab→XYZ 100k: **18.1 ms** (mojo
  1.31 ms = 13.8x). NumPy sRGB→XYZ 50k: **5.13 ms** — comparable to the mojo
  wrapper's 5.5 ms, confirming the sRGB path is the least mojo-advantaged row
  among the big kernels (NumPy's `**2.4` is C-level; the mojo `pow` is the
  same cost class, hence the §"unroll" recommendation targeting exactly this).
- Upstream colormath object-loop times (20k–100k objects): Lab→XYZ 100k loop
  **997 ms** (mojo array 100k: 1.1 ms), sRGB→Lab 50k loop **1308 ms** (mojo
  9.1 ms), Lab→XYZ 20k **194 ms**, XYZ→Lab 20k **183 ms** (mojo arrays:
  0.23 ms / 1.38 ms respectively).

## Things this analysis does not claim

- No GPU measurement was made (no GPU on this box). GPU verdicts above are
  from arithmetic intensity + transfer-cost arguments only, which is why they
  are all "none"-adjacent.
- Timing noise is ±10–25% run to run (notably the upstream matrix rows).
  Crossovers below n=16 for CIE76 should be read as "tied within noise."
- The `README.md` "~3 GFlop/s" historical claim and the "52.51x before
  optimization" history sentence are not reproduced anywhere in this session's
  data and should not be quoted as facts.

## Reproduction

`pixi run bench` reproduces the headline table. The analysis rows additionally
used best-of-5/7/9 loops in temporary scripts under `/tmp` (not committed),
varying n ∈ {1…1M}, calling raw ctypes bindings with pre-made buffers to split
glue from kernel, and single-calling scalar edges 20,000×.
